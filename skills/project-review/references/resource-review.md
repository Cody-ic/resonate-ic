# 开发资源检查与核验范围

开发资源供别人接入，应有较好的可靠性；按声明的用途和范围检查，不能把“尚未完成核验”推断成“明确不能用”。作者在 verification 中声明当前版本已做的步骤、适用范围、未核验部分和可选证据。声明不是平台认证；不得把作者写“稳定”当作已完成实测的证明。AI实际检查与作者声明须分别表述。

## 决定标准

- pass：实际读到核心资料、能明确说明本次检查范围，未发现证据充分的阻断问题。允许作者如实声明未打样、未实测、未跑DRC，允许附带未完整读取的其他材料；在 limitations 写明。ready=true 仅表示可按声明范围收录，不表示整板或所有功能可靠。未实测本身不是拒绝理由。
- revise：只有充分证据证实、可定位、影响作者声明范围内核心功能、正常接入或安全使用的明确问题。须同时给出具体文件/对象字段、真实原文、成立的依据、关键前提、推导和实质影响。陌生写法、不常见参数、通常可能有风险、没有提供视频、缺少某项检测，不能成为打回理由；高置信度不代替证据。广告等内容拦截仍按普通发布规则独立处理。
- disputed：核心资料无法读取、当前检查无法形成有范围的有效结论，或存在有具体依据的事实冲突。说明“检查未完成，不是不合格或已确认缺陷”；当前版本暂不公开。纯技术未知不要求作者或管理员代替AI给整板作可靠性认证；只说明具体缺口，能补材料后再检查。不要编造 findings 来凑阻断证据。

## 充分证据与 PCB 边界

每个 reliability finding 必须有 confirmedIssues 对应项：source 为实际读取的文件路径，quote 为该文件中的真实片段；basisQuote 是实际读到的判断依据（源码、相关记录、已提供手册/检测结果或作者明确的支持范围），reasoning 解释从依据到结论的推导，impact 和 affectedScope 说明实质影响及适用范围，preconditionsConfirmed=true，uncertainties=[]。关键前提仍有未知时不能确认缺陷。引文存在只证明来源真实，不能替代推理和前提核实。

PCB读取器只提供 EPRU 原生对象分段，并未执行EDA、ERC/DRC、导出钢网或实物测试。必须关联PCB中的器件与对应封装文档；不能把库焊盘的空网络当作整板未连接。没有手册时不得仅凭型号猜封装要求。计算 paste 开口应区分原始面积之和与有效并集面积；尺寸/单位、EDA扩展语义或叠加规则尚未确认时只能作条件分析，不能断言制造缺陷。极大负扩展可能用于收缩至无自动开口，不因数值极端就判错，也不要求无实际影响的底层字段清理。

例如：自动开口叠加四小窗口后可能成为100%，可定位为需核实风险；若EDA合并语义和作者目标尚未证实，不足以打回。若实际制造导出和已确认的设计要求证明应为四窗口、实际却完整开口，才可据此提出明确修改。不得以局部封装检查代表整板认证。

检查源码、接口、示例与验证资料时，目录、测试脚本存在不等于已经运行。只列对使用有实质帮助的建议，不列风格、小遗漏或作者已标明的未验证项；未读材料不声称已检查。资源修改版本独立审核，期间保留原公开版本。

## 输出与作者通知

resourceReliability={ready,reason,checkedScope,evidence:[{quote,explanation}],limitations:string[],confirmedIssues:[]}。checkedScope 至少明确具体对象/功能及检查方式，不能只写“审核通过”。无已确认缺陷时 confirmedIssues=[]。pass 时 findings=[]，evidence 至少一项来自实际读取的资源资料；资料无法读取不能仅引用投稿文字宣布完成检查。

无论通过、打回或未完成，都输出 authorNotice（title、body），供站内和邮件共用。通过时简短感谢，说明范围而不宣称全面认证；打回时列明充分证据、影响和必要修改；未完成时委婉说明具体未知项。别说已发邮件、已运行或已公开。有实质建议的文案仍按现有人工确认流程发送，避免无关小建议。资源收录不自动构成精选。
